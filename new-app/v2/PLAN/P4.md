# P4 — Calendar & days

**Goal:** the planner identity: days own plans, lazily forked from the library; the calendar browses them; day boards run them.

**Phase verification:** **user checkpoint** — browse the week, plan tomorrow (it materializes), run today, edit the routine and watch *later* days pick it up while lived days stay frozen.

---

## P4.1 — Day model + lazy fork

**Goal:** `date → plan` with the placeholder/fork lifecycle (OVERVIEW §6) — the rules pinned at storage level before any UI.

1. **Storage**: `Days` (date PK → `planTimerId` nullable = nothing configured) where `planTimerId` points either at the **library plan** (placeholder) or the day's **own materialized timer** (`dayDate` column on Timers); `originPlanId` provenance for save-to-folder.
2. **Placeholder resolution**: a day with no explicit plan resolves via P3.4's rules; **reads never materialize** (board render + calendar counts read through).
3. **First write materializes**: plan edit / checkmark / adjustment / run start → copy the plan tree (as it stands) into the day's timer with **marks cleared** (P1.1's rule), then apply the write. Everything after is ordinary v1 machinery (the tweaks-#8 live editing works on the copy unchanged).
4. **Lifecycle invariants**: library edits reach future days by arrival (forks happen on use) · a materialized day never tracks the library again · **save to folder** is the explicit write-back (marks cleared).
5. Migration: v1's boards/timers become library plans (P3.2's note); no day rows until the calendar creates/uses them.

**Pinned tests:** read-through without rows (board render + count paths) · each first-write trigger materializes exactly once · marks cleared on fork · post-fork independence (library edit doesn't touch it) · placeholder picks up later library edits · provenance round-trip.

## P4.2 — Calendar page

**Goal:** the outline's calendar view.

1. **Views**: week (default; settings later flips the default) and month — both are the outline's *list of days*: `Monday … 3` rows = day name + interval count **read through the placeholder**. Month view = the month's days as rows (same row shape).
2. **Highlighting**: today highlighted; the date-setter's chosen day highlighted (and navigates to its week/month).
3. **Navigation**: hover `</>` chevrons at the center edges (the touch-map's swipe replacement — not covering content) = previous/next week/month; tapping a day opens **that day's board**.
4. **Date setter** (bar button): popup **month-grid** picker (the boring default for the outline's "html calendar" open-idea).
5. Calendar bar: **home · view toggle (week↔month) · date setter** (the outline).

**Pinned tests:** day rows + counts (placeholder and materialized) · highlight rules · chevron paging (both views) · date-setter navigation + highlight · tap → day board.

---

## P4.3 — Day boards

**Goal:** the board bound to a date, plus Home.

1. A day's board = the standard board (P2) bound to a date: placeholder or forked render **identically** (the user must not be able to tell which they're looking at).
2. **Day swiping**: hover chevrons = previous/next day (date-bound boards only).
3. **Home**: the bottom-bar home button = the current day's timer (P5.2's setting may point Home at a specific plan instead; the seam lands here).
4. The full **fork lifecycle is the acceptance story** of this phase: open tomorrow (read-only), edit/check/run → materialized; edit the routine → the day after picks it up; yesterday frozen.

**Pinned tests:** day-board binding + chevrons · placeholder/fork render parity · home resolution (current day / specific plan seam) · lifecycle integration test (the paragraph above as one test).
