# P5.1 — Alert firing pipeline (sound + KDE notification)

**Goal:** The real thing users feel: when an interval hits zero, Planner plays the chosen mp3 AND shows a KDE notification — always, even with the app focused. Notification click focuses Planner.

**Prereqs:** P1.4 (engine events), P2.1 (adapters), P3.2 green.

**Read-first:** P1.4 §2–3 (alert decisions + fallback); P2.1 §1 (KdeNotifier/Mp3Player); D-decisions on always-alert.

## Tasks

1. **Pipeline:** engine `PlayAlert` event → `Mp3Player.play(resolvedFile)` + `KdeNotifier.notify(title: timer name, body: "N. <interval name>")`. Fire regardless of window focus/state (running in tray included — app process alive by design, D5).
2. **Resolution at fire time:** engine's pure resolution (P1.4 §3) fed a fresh directory listing at event time (file may have been added/removed since edit).
3. **Notification click** → bring Planner window to front. **No action buttons** (parked — see FINAL-APP-OUTLINE.md; stretch only in P6.1).
4. **awaitingAdvance UX at zero:** for manually-complete intervals, the alert + notification fire at zero while the board shows the tap-to-continue affordance (P3.2); opening the app and advancing is the v1 unpause path. Sound plays once (no repeat policy).
5. Edge: overlapping alerts queue; app quit mid-alert stops sound.

## Required tests

- Widget/integration with fakes: zero → notify+play called with right args; focus-independent (simulate hidden window state flag).
- Fallback at fire time (missing file → default; empty dir → notify-only).
- Manual desktop checklist (in report): real alert fires in-focus, out-of-focus, in-tray; click focuses.

## Definition of Done

`flutter test` + `dart test` green; user hears/sees a real end-of-interval alert on their desktop; committed.

**Out of scope:** notification buttons, pre-warnings, vibration, repeat-until-acked.

- **Notification copy** per this part (supersedes P2.1's placeholder): title = timer name, body = `N. label` (ordinal+1, 'Interval' fallback).
- **Focus-independence is by construction**: nothing in the pipeline consults window state; the app process lives in the tray (D5) and the 1 Hz heartbeat settles + flushes regardless. The test drives the controller with no widget tree at all.
- **Sound plays once, no repeat policy** (v1 slice); overlapping alerts queue FIFO in Mp3Player (P2.1); process exit stops playback implicitly (GStreamer teardown) — `stop()` is wired for selection-change/exit in the alert selector (P4.3).
- `PLANNER_SMOKE=alert` added alongside `PLANNER_SMOKE=1`; smoke uses an in-memory DB (drift promoted to a regular app dependency for this) so the real change log stays clean.

How to verify by hand — CHECKPOINT (user):
1. Put an mp3 in `~/.local/share/planner/sounds/` (e.g. `ding.mp3`).
2. Create an interval with that end alert (right-click dial → editor → + → End Alert), a short duration (e.g. 10s), auto-finish ON; Done; start the timer.
3. Matrix: with the window focused → hear the mp3 + see the notification; unfocused → same; app in tray (close window) → same.
4. Click the notification → Planner window comes to the front.
5. Repeat with a manually-complete interval: alert fires at zero, board holds `00:00` + tap-to-continue; advancing continues the chain.
6. `PLANNER_SMOKE=alert ./planner` (from the release bundle) fires one synthetic alert on demand.
