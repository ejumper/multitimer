# P1.4 — Events, end-alerts, terminal-state logging

**Goal:** Close the engine loop: end-alert decisions, terminal-state persistence to the change log, and the engine-side alert resolution logic (which sound file, with fallback) — all as pure logic fed by P1.3's event stream.

**Prereqs:** P1.3 green.

**Read-first:** P1.1 §3 (change log), P1.3 §5 (terminal emissions); `multitimer-spec/FINDINGS/background-and-alerts.md` §5 (reference: how MultiTimer structures alert config → playback; we implement a thin slice).

## Tasks

1. **Event bus consumption:** engine subscribes its own session events and (a) appends terminal-state entries to the event log via `Store`, (b) decides alerts.
2. **Alert decision:** at instance zero (BOTH finish methods — a manually-complete interval reaching zero alerts too), if `endAlertSoundFile?` non-null → emit `PlayAlert {soundFile, timerName, intervalName, ordinal}`. No pre-warnings, no repeat policies, no vibration (v1 slice).
3. **Sound resolution (pure):** given requested file + the known sounds directory listing → if file exists use it, else fall back to **first file alphabetically** in the directory; empty directory → `null` (no sound; still notify). Directory listing is injected (no `dart:io` in engine).
4. **Run-log entries:** terminal events `{ordinal, defId, terminal, timestampMs}` appended (this is the history/completion groundwork — data only, no UI ever in v1).

## Required tests

- Alert fires at zero for both finish methods; not on skip (skipped ≠ alerted — decide: no alert on skip, document).
- Fallback: missing file → alphabetical default; empty dir → silent+notify-only.
- Terminal entries appear in change log, ordered, one per ended instance.
- Warp-clock integration: full session run (start → several intervals → manual advance → finish) produces the complete expected event sequence.
